# 本地占用与缓存清理

在用户要求清理、核对占用，或 goal 新轮磁盘检查达到下列阈值时使用；不作为每轮机制验证的收尾步骤。

## Goal 每轮开始检查

用户 2026-10-11 要求：每次完成 goal 的新轮开始先检查 C、D 盘；C 盘小于 5 GiB 就重启 Unity，D 盘小于 3 GiB 就整理项目并删除不必要的东西。比较实际剩余字节数，阈值分别为 `5 * 1GB` 和 `3 * 1GB`（PowerShell 的 1GB 为 1024³ 字节），严格小于才触发，不用四舍五入后的显示数字判断。

```powershell
Get-PSDrive -Name C,D -ErrorAction Stop | Select-Object Name,Free,@{Name='FreeGiB';Expression={$_.Free / 1GB}}
```

检查结果和处理写入本轮已有记录即可，不另开验证批次。读取失败先排查，不将失败当作空间达标。未达阈值时直接继续原工作；两盘同时触发时分别处理并复查。处理后仍低于阈值时报告实际余量和已做操作，避免循环重启或扩大删除范围。

C 盘低于阈值时，先保存本轮已完成结果和续跑位置，停止正在操作的 Play 模式，保存有改动的场景及资产，再正常关闭当前 MTGB Unity Editor 并以同项目、同版本重开；不强制结束进程或丢弃未保存场景。已获用户授权，无需每轮再次询问；若 Unity 未打开，无须为释放缓存新开编辑器。重启后核对目标项目、编译与连接状态，再按原记录续未完成差异，不重跑已完成场景，也不把重启标作用户暂停 goal。

D 盘低于阈值时，按本文件的占用检查、进度账本引用核对和证据淘汰规则清理项目。优先明确可再生成的过时工作区缓存和编译中间文件；记录精确目标、理由与实际释放量。保留卡图、运行资料、录屏工具和仍被账本引用的证据；不为释放空间删除未知文件，也不清理正在使用的主编辑器 Library/Temp。该阈值维护不执行 Forge/Unity 机制回归或全量覆盖刷新。

维护依据：新增用户阈值规则；旧规则“仅在用户要求清理时使用”已扩展为包含每轮开始的条件处理，原证据保护及安全删除范围保持。此次实际检查 C=20.57 GiB、D=14.18 GiB，未触发重启或删除。

先统计项目根目录各子目录的文件字节数，含隐藏目录；遍历不跟随 junction／symlink，单列链接与不可读项。区分逻辑大小、去除硬链接重复后的文件大小和真实分配空间，不能混用。Windows 的 os.scandir 缓存 stat 可能返回 inode/nlink=0；需要硬链接去重时用 os.stat(path)，不可把所有零 inode 当成同一文件。数字注明 GiB（1024³）或 GB（1000³）。

本项目 CardImages 包含英文、zh-CN、ja-JP 卡图；.tools 下不仅有缓存，还有机制历史批次、输入快照、源码归档、失败和截图。.codex/validation 是旧验证工作区，Library 等生成目录仍可能占用数 GiB。不要按“隐藏／被 Git 忽略／旧日期”直接判定可删。

用户所说的“缓存”包括无用、过旧且已有替代的临时产物，不限于 Unity／Python 可生成缓存。可清理对象：确认未被进程使用的验证工作区 Library／Temp、临时 Python __pycache__、可重新下载的明确工具包缓存及编译中间文件；旧构建和升级前备份先对比运行包版本、检查消费者及在用进程。保留本轮有效工具，尤其项目未完成时仍需使用的录屏提帧工具。主 Unity 编辑器打开时保留其 Library／Temp 和包缓存，不为清理强行关闭用户编辑器。检查 Unity 项目参数及导入工作进程，输出只需项目路径／PID，不打印可能带敏感参数的整个命令行。

保留：卡图与下载缺口记录、Assets／Packages／ProjectSettings、ForgeRuntime、Git 历史、原始录屏、当前基线及仍被进度账本引用的结果／manifest／输入和取证源码。历史证据不是普通缓存；用户明确要求删过时验证时，可按下面的证据淘汰规则清理，无须再次询问同一授权。

## 用户要求淘汰旧验证

读取 latest.json、unity-latest.json、verified-progress.json 的 baselineEngine／baselineUnity 与所有证据路径；再检查当前机器可读报告的引用。按来源版本和任务区分旧批次，不能仅按日期。优先选早于保留完整基线、所有登记任务都 PASS 且新基线包含这些任务／不少于原场景数、没有当前账本引用的批次。这个任务级比较仅用于淘汰旧版本资料，不宣称不同版本的全部断言语义相同或当前全池通过。

保留当前完整基线、近期增量证据、唯一规则断言、未解决失败／中断和未知覆盖项。不跟随指向项目外的 junction 清理。删大体积输入／截图／日志前保存小型 results.json、原版本与哈希、淘汰原因及保留基线，明确标记历史大文件已删；旧 Markdown 的历史记录不再作为可重放证据。未实际删除时保持 planned/blocked，不能把候选清单登记为已清理。

删除前保存精确候选目录、大小和理由。所有递归删除使用 PowerShell 原生命令并验证解析后的绝对路径在项目内；候选不是链接，祖先也不得跨出工作区，不通过 cmd 或拼接命令删文件。清理后重新统计，并确认目标缓存已移除、保留数据仍存在，记录实际释放量。目录中含未知或不可重建内容时先缩小到明确缓存子目录。

仍被引用的大体积 JSON／JSONL／日志可用 NTFS 压缩保留原路径，不能把压缩说成删除或逻辑大小减少。先记录精确文件清单、SHA-256 和压缩前存储字节，执行后核对内容哈希与存储字节；记录卷空闲空间变化，区分其他进程同时写入的影响。PNG／JPEG／视频／压缩包通常已压缩，不作为主要压缩对象。2026-10-10 的盘点发现 `.tools` 验证产物大于卡图，后续占用判断先看文本取证和重复产物，不能默认卡图是唯一原因。

### 大型证据的压缩升级

继续整理且用户排除 Unity 生成缓存时，先核对下载包与保留运行包的逐文件哈希，清理确认重复的下载副本；当前引用的证据按原路径保留。对大型、很少修改的历史 JSON／JSONL／文本日志，先选代表文件试用 `compact /EXE:LZX`，比较存储字节并核对完整 SHA256。普通 NTFS 压缩转换时逐文件解压再压缩，预留临时空间；失败时恢复普通压缩并记录原内容核对结果。

试验有明显节省后，保存精确清单及每个文件的操作前哈希，再分批升级。原路径、逻辑长度和内容哈希全部核对通过才计入节省；硬链接文件单独处理，避免重复计算或并发操作同一文件。压缩状态结合存储 API 与 compact 输出确认，`FILE_ATTRIBUTE_COMPRESSED` 单一标志不能涵盖 LZX。删除量、压缩节省和卷净空闲变化分别汇报。

2026-10-14 的反例：只删除过时构建释放约 2.4 GiB，并不代表剩余无优化空间；约 50 GiB 的 `.tools` 逻辑长度也不能直接当实际占用。追加试验中一份 321,910,672 字节的历史日志，从普通压缩的 121,147,392 存储字节降为 LZX 的 13,279,232 字节，SHA256 保持。全部执行、文件哈希和实际收益见 `.tools/workspace-cleanup-1014/compression-probe.json`、`compression-plan.json`、`compression-journal.jsonl`、`compression-result.json` 与 `deeper-summary.json`。

清理只需要文件和占用检查。维护 skill 运行 quick_validate 即可；不触发 Unity 对局、Forge 效果套、全机制覆盖刷新或恢复暂停的 goal。

工具自动审查拒绝删除时，保留候选清单和拒绝原因；只有真正更小、不同风险的允许操作才能继续，不能换脚本／工具绕过同一拒绝。结果明确分为已删、未删与实际释放量，不能把“清理计划完成”说成“缓存已清理”。2026-10-05 的部分操作曾返回 blocked by policy；这是旧操作结果，不代表后续用户手动清理或新环境中不同目标的结果。以各批次执行日志为准。
