# MTGB 产品目标与当前缺口评估

> 后续更新（2026-09-05）：本文保留当时的审计/导入记录。制卡基础现已升级 schema v8，Lua 嵌套回调与多库身份、内容分类已修复，最新状态见 [制卡基础验收](AuthoringFoundation.zh-CN.md)。
评估日期：2026-09-05。

根据后续讨论整理的执行清单见 [当前开发待办](DevelopmentTODO.zh-CN.md)。其中已纳入官方多库、编辑器定义分类的要求，并将 ZIP 支持和目录结构明确列为暂缓决定；本文中的卡包管理方案属于评估建议，并非全部已经定案。

目标：提供 MTGA 式自动规则对局体验，同时允许玩家通过独立 Data Editor、卡图和 Lua 制作、分享并联机使用 DIY 卡。常见效果应容易制作；复杂效果应通过通用接口组合，不要求作者修改 C# 或重新编译客户端。

已确认的多库需求：官方内容也按系列扩展包拆分为多个数据库，DIY 数据库与这些库同时加载。多库是正常产品形态，不应要求合并到 core.mtgbdb。优先评估已有 PrintingKey（系列代号/收藏编号）作为跨库印刷身份；新增卡包命名空间只是候选方案，尚未定案。相同身份的覆盖策略与不同卡牌碰巧具有相同库内整数 ID，必须分别处理。

已确认的内容分类需求：由作者在 Data Editor 中定义卡牌内容分类，运行端读取该分类，并支持按官方、DIY 等类别搜索和筛选。用户以 YGO 的 OCG/DIY 分类及搜索作为交互参照；具体字段、取值和是否允许组合尚未定案，不直接照搬 YGO 枚举。该功能已在用户规划中，目前尚未接入；数据库文件名与卡牌内容类别是不同维度。

本次依据当前工作区、独立编辑器本地源码 `D:/WorkSpace/MTGB-DataEditor` 和已有验证记录进行静态盘点，没有重新运行 Unity、编辑器或双客户端验收。编辑器结论针对本地源码，不代表已发布版本。以下优先级针对产品目标，区别于旧 DEVELOPMENT_GAPS.md 中按模块划分的优先级。

## 总体判断

已有可继续建设的规则、数据、脚本与联机基础；尚未完成面向普通作者的制卡闭环，也未把新版战场接成完整对局入口。

“维护者能添加几张测试牌”只证明部分技术路径可用。“玩家能够独立制作、测试、分享新卡，另一位玩家安装后正常对战”才是首个产品里程碑。

不以接口数量、测试牌数量或视觉截图估算完成百分比。分别记录：实现存在、数据校验通过、规则行为通过、实际交互通过、实际网络通过。

## 已有基础，应保留并继续验证

- Schema v7 数据库、外部卡图与 Lua 路径契约、独立 Data Editor。
- 编辑器已有卡牌与特殊结构编辑、Lua 编辑、代码补全、签名提示和基础脚本模板。
- Lua 有事件、触发、启动、目标、费用、选择、持续与替代效应等公开接口，并有版本、执行配额及错误定位基础。
- GameAction、确定性状态与回放、优先权、堆叠、战斗、目标和费用等规则基础。
- 权威服务器、玩家视图脱敏、房间、内容哈希、重连、BO1/BO3 和换备实现。
- 新战场的环境、卡牌、手牌、HUD、检视等视觉组件。
- 2026-09-04 记录显示两个测试牌组各 16 局规则回归与全项目验证通过；专项牌批次没有完成实际双开 UI 验收。

## P0：打通 DIY 制卡与使用的关键障碍

### 1. 修复通用效果组合的引擎限制

**已确认的代码限制：** `LuaCSharpCardScriptRuntime.ExecuteWithInstructionBudget` 拒绝 Lua 执行期间再次进入 Lua，抛出 `Nested Lua execution is not allowed.`。已有专项文档记录了 Lua 效果触发自定义 Lua 替代筛选/处理回调时的问题。

对产品的影响：作者可以分别找到伤害、区域移动和替代接口，但把它们组合起来仍可能失败。内建替代操作通过，不能代表自定义替代回调可用。

验收：由 Lua 发起的事件能按规则调用适用的自定义替代回调，保留正确的事件上下文、资源限制和规则顺序；通过实际脚本组合回归及联机验证。修复必须是通用能力，不能针对测试卡名或编号加分支，也不能仅删除保护检查。

### 2. 对齐编辑器、SDK 文档与运行端

**已确认的版本漂移：** 本地 Data Editor 的 `MainForm.BuildDefaultScriptText` 仍生成 `ApiVersion = 1`，`LuaSdkCatalog` 也有 API 1 提示；当前运行端支持 API 2，制卡规范要求新脚本声明 API 2。

这不等于 API 1 脚本必然加载失败：运行端目前拒绝的是高于支持版本的声明。但作者入口与当前规范不一致，说明编辑器和引擎的 SDK 同步尚未收口。

验收：模板、补全、参数提示、常量、示例和文档与同一版本运行端匹配；作者创建普通牌和特殊结构牌时无需手工修补生成内容。建立可检查的 SDK 同步方式，避免靠维护两份手写目录长期保持一致。

### 3. 让多个作者的内容可以可靠共存

**已确认的运行行为：** `CardDatabaseRepository.LoadDatabase` 按全部加载数据库检查内部数值 ID；重复 `card_id` 会记录警告并跳过卡牌。不同 printing key 也不能绕过这个检查。

对产品的影响：两个独立作者的数据库若包含相同内部 ID，合装后可能少牌。当前由维护者扫描全库再分配 ID 的导入方式不能代替作者之间互不协调的分发流程。

验收：明确稳定的内容身份与安装冲突处理方案；两个独立制作的卡包可一起使用。真正同身份冲突需向玩家明确解释，不能让玩家靠 Unity 日志发现少牌。方案需保持数据编辑器、牌组、脚本关联与联机身份一致。

已规划但尚未接入的内容分类：当前 `customContent` 仅通过数据库文件名是否为 `core.mtgbdb` 判断，其他文件均标为自定义内容。这是需要替换的临时实现，不代表产品打算按文件名分类。按用户明确的方向，在 Data Editor 增加可编辑分类，保存到数据中，由运行端读取，用于卡牌搜索、牌组编辑筛选和房间内容限制。验收时应确认多个官方系列库不会仅因文件名不同而被当作 DIY。

### 4. 做成可操作的内容包使用流程

已加载多个数据库及内容哈希检查是基础，但还不等于作者可理解的卡包管理。

**已确认的当前粒度：** `OnlineContentManifest.Build()` 对 `CardDatabaseRepository.LoadAll()` 生成整体内容哈希；连接握手校验这份清单。多装一份改变加载内容的 DIY 数据库，也可能导致连接被拒绝，现有错误主要区分数据库和 Lua 两类。

验收：明确包身份、版本、所需引擎/API、文件集合、安装检查和冲突提示；玩家能知道缺哪个包或哪个版本。房间选用的内容集合应覆盖对局中可能生成、引用的内容，不能简单只算牌组内卡牌。

遵守现有 ADR 0002：作者在外部分发内容包，玩家与服务器安装相同版本；不把公共上传平台或大厅自动传包作为本轮前置条件。

## P1：让制卡容易，让 DIY 卡自然接入对局

### 5. 建立作者能自己完成的测试流程

现有专项检查主要是维护者编写的 C# 验证套件与 Unity 命令，双重数据校验契约也已存在。尚需证明普通作者能在不写 C# 测试、不读 Unity 内部日志的情况下定位问题。

建议提供常见效果模板和最短制卡教程，覆盖抓牌、伤害、目标、进场触发、额外费用、持续效果、替代效果和多步选择。进一步提供可重复的试牌场景：安排手牌、法术力、目标和阶段，显示脚本错误及关键事件结果。

验收：作者从空白卡开始，完成数据与图像、脚本、校验、试牌、修改和重新测试；结构正确、脚本可加载与行为正确分别显示。无需每张新卡改引擎或另写一套 C# 工具。

### 6. 把新战场接成完整规则交互

主菜单和联机目前仍进入 `MTGAPrototype`。新场景已有点击手牌出牌与地牌启动操作，但战场点击仅处理本方地牌，未完成通用目标、非地异能、攻击与阻挡等交互接入。

区域堆点击处理为空；设置按钮为空；手牌拖拽尚未接入；决策计时是本地展示倒计时，未接权威时限及超时规则。

验收：Lua 声明的目标、费用、模式、排序、数值和选择能通过通用 UI 完成；双方都能响应、取消允许取消的宣告并理解拒绝原因。常见新卡只增加内容，不新增专属 UI 代码。完成后再把正式入口切换到新战场。

MTGA 式体验的首要验收是操作清晰、规则可理解、交互完整，视觉与动画继续迭代。

### 7. 用真实客户端验证端到端流程

先利用已有旧战场验证最近规则修复和实际网络流程，作为迁移交互的基准；再在新战场重复验收。

覆盖两席操作、响应反击、部分目标失效、费用选择、同时选择、选择期间断线与恢复、对局结束及 BO3 换备。固定策略规则回归、玩家视图 JSON 往返、真正传输网络包、鼠标操作分别记录，不互相替代。

## P1 后续：持续扩大已验证的规则与 DIY 表达范围

- 历险被反击或被替代去往其他区域，传纪章节目标与反击，多种替代效应顺序、复杂同时区域移动、控制权/类别/颜色/异能依赖、生命支付边界等，应作为具体测试场景逐项验证；未覆盖不等于已确认有 bug。
- 特殊牌结构已有数据与运行时入口，但每类仍需真实内容、Lua 行为和实际交互验证。
- “能改变规则”需逐条证明。当前 SDK 文档列出 MaxHandSize、LandPlaysPerTurn、CastAsThoughFlash 等规则键；通用注册接口的存在不能证明任意自定义胜利条件或全新规则已经支持。对新需求明确区分已有接口可组合、需补通用接口、以及未来比赛变体。
- DIY 不要求预先完成所有历史官方卡牌，也不意味着无限制地承诺任意新机制。公布已验证规则范围，优先补充阻碍多类卡牌的通用能力。

## P2：规模化与扩展

- 性能分析、长期多房间压力测试、可重复客户端与服务器发布、对局记录和错误诊断。
- 继续改善动画、音效、设置、可读日志、回放等体验。
- 更大官方牌池与 DIY 示例库。
- 账号、匹配等服务按实际需要推进，不作为朋友之间安装同版 DIY 包并联机的前提。
- 指挥官与多人按 ADR 0001：先稳定双人 LAN，再泛化为 2–4 玩家核心模型，然后实现指挥官交互；新增代码避免继续固化双人假设。

## 下一里程碑与执行顺序

里程碑：一位不参与引擎开发的作者，从独立编辑器制作一个代表性 DIY 包；另一位玩家和服务器安装后，双方可在完整战场里完成对局。全程只增加数据、图像、Lua 和内容包配置，不修改卡牌专用 C#。

建议顺序：

1. 同步编辑器 SDK，复现并修复 Lua 组合执行限制。
2. 明确多作者内容身份与卡包安装/联机内容集合，做两个独立包共存的验证。
3. 用代表性 DIY 包走通作者制作、试牌和真实双客户端对局，完善模板与错误反馈。
4. 把已验证的通用交互接入新战场，重复整条流程，再切换正式入口。
5. 按新卡需求扩大规则覆盖，再开展更大牌池、性能与发布工作。

这几步不必等所有规则边界穷尽才开始，但每一步都要有明确的行为验收。
