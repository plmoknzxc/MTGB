# 牌库浏览：完整槽位与已知位置（2026-10-16）

本轮按用户反馈修正牌库浏览；沿用“暂不打包”的要求，仅修改源码、Editor 和隔离原生测试类。旧机制 goal 仍暂停，桌面客户端、更新 ZIP、根 ForgeRuntime 与公网均未更新。

## 原因与改动

旧 `RefreshZoneBrowser` 对非局后完整牌库只取 `libraryTop`，没有已知顶牌时得到空数组，因此有牌却空白；即使有顶牌也不能表达底部或中间位置。

- 根据公开的 `libraryCount` 生成全部位置，从顶至底编号；每页至多 10 张，跨页保持绝对编号。未知槽位为真实牌背，不含服务器物理 ID、印次或正文。
- 新增稀疏 `libraryCards`：只传接收者有权知道的牌面、从顶数起的 1 基位置和明确公共标记，不传整副隐藏牌库。旧录像／旧服务端无此字段时仍显示完整牌背和旧已知顶牌。
- 公开单牌置顶／底或固定位置、私有占卜及已选择的入库顺序分别记录；身份与位置均验证才显示。抓牌后已知底部按新张数编号；洗牌清除相应库的旧位置。不能确认的位置回到牌背，不能按服务器秘密顺序猜。
- 私有排序与公共观察分开。多个公开来源的牌一起入库，不代表其所有者的排序公开；每个所有者只有一张的情况没有该顺序歧义。观战端只保留明确公共记录，客户端也再次守卫。
- 普通浏览点击只看详情；原生优先权明确提供的施放按钮继续可用。禁止从未知卡背生成操作，新的请求会撤销旧按钮。

多牌入库的私有顺序依据：Wizards [2026-09-25 综合规则](https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.txt) 401.4；公开来源不使所有者选择的顺序自动公开。实现只读观察原生结果，不改卡牌规则资料。

## 原生与桥接验证

证据集中在 `.tools/library-browser-1016/`，真实流程只用 `StateBranchFixture` 安排开局，后续施放／激活、选择、抓牌、洗牌由 Forge 执行。受测类来自该目录的 `classes`，置于既有运行包类之前；实际加载身份与每个 class 的哈希保存在结果中。`baseRuntimeHash` 仅标识原始底包，不冒充已安装新版本。

| 实际流程 | 本轮断言 |
| --- | --- |
| Opt | 私下占卜置底、随后抓牌；原物理 ID 在当前库底，只对原查看者提供牌面 |
| Hallowed Burial → Divination → Elixir | 双方各一张生物公开置底、抓两张后编号变化、实际原生洗牌事件后的隐藏 |
| Hallowed Burial → Divination → Evolving Wilds | 自己搜索并洗牌后清除旧位置，另一方未洗牌的已知底牌保留 |
| Temporal Spring | 已保存真实流程中准确目标的物理 ID 在双方位置 1，支持缺省顶位置；驱动误猜目标见下方 |
| Approach of the Second Sun | 实际结算后公开处于从顶数第七张，双方一致 |
| Hallowed Burial，自己两张不同生物 | 排序者保留准确底部次序，对手不能获知这两张的私有顺序 |
| Mishra’s Bauble → 对方抓牌 | 原有私下检视仅给查看者，普通抓牌不向任一方新增卡面窗口 |

确切当前结果路径、检查和哈希统一见 `audit.json`。这些是有界规则／权限结果，不是全卡池、完整公网长局或新版内存基准。

“第七张”首次复验失败，原因是桥接只取堆叠根异能，实际移区由子异能发起。`GameAction.fireZoneChange` 现在只在原同步通知期间提供准确 cause，finally 恢复，支持嵌套；移区、替代、触发及旧 Craft／Meld 补丁原逻辑保持。完整当前 GameAction 与全部已登记补丁重新应用的结果逐字一致。该新增原生类必须和桥接类一起发布，不能只更新客户端 DLL。

## Unity 展示验证

- 旧逻辑先复现 4 项失败：隐藏牌库没有槽位、公开底部没有准确位置；修正后首轮 4 项通过。
- 最终 140 项 UI 检查：三语、三档字号、实际牌背与卡图、每页数量／绝对编号／底部标签、详情只读、同名多实例、非法位置、局后完整库、客户端及服务端观战守卫。这里的 12 张数据是明确的合成布局样本，不计规则效果。
- 实际 Forge 结果快照接入当前 UI，共 20 项通过：私有置底双方、公开底牌、私有排序双方；按实际接收视图检查牌背／牌面、页数、底部编号、观众投影和无游戏提交。截图 `native-public-1-final.png` 为已关闭通知窗口后的真实结果重放。
- 独立 6 项合成优先权适配器边界通过：合法选项、准确提交一次、禁用选项、未知槽位、请求更新移除旧动作、浏览无额外提交；不当作真实“从牌库施放”规则效果。
- 原选牌提示去重和 viewport 修正保留，仍以先前 `.tools/picker-layout-1016/` 的独立证明为准，不把牌库样本当成对它的重新全量验证。

## 保留的失败、更正与边界

1. `public-bottom-knowledge-before`、`public-bottom-final` 等早期测试错误假设 Elixir 只洗自己的库。实际调用栈显示 `ChangeZoneAllEffect` 会执行它所选玩家的原生 shuffle，另一方也收到真实洗牌；不是 LKI 刷新。尝试的 StackWalker 过滤已完全移除。后用 Evolving Wilds 独立证明未变化库的保留。
2. 搜索驱动先漏处理 `InputSelectEntitiesFromList`／排序请求；保留 FAIL，不修改生产选项绕过原生。
3. 多牌权限守卫最初按全列表而未按所有者分组，误隐藏双方各一张的公共位置；修为逐所有者判断，保留前后结果。
4. 第一版截图驱动重复打开详情／在延迟销毁同帧截图，截图仍被详情覆盖；截图不能作为布局通过。最终真实结果重放先关闭通知，等待稳定帧后取纹理，已逐图检查。140 项检查与可见截图分开记录。
5. 施放边界初始合成输入给优先权选项塞入 `card`，被生产逻辑识别为牌面选择窗口；修为实际优先权的 ID 选项形式后通过，旧失败保留，不把驱动错误当成规则缺陷。

6. Temporal Spring 驱动选择了首个合法目标 Plains，却错误期待预置的 Grizzly Bears。未重写原 FAIL；用已保存堆叠目标和结算后双方快照逐物理 ID 独立核验通过，记录 `top-verified.json`，不为驱动误判重复施放。

位置无法确认时保守隐藏，例如未专门跟踪的混洗／重排和中间固定位置的后续复杂变动；不声称永久记住所有历史已见牌。旧服务端没有新增稀疏位置字段，需未来两端及原生一起更新后才会在实服看到这些底部／中间牌面。

机制覆盖工具仅刷新分类（不带 `--run`），未把历史任务改授当前 PASS；本轮不恢复暂停 goal，不执行部署或重新打包。
