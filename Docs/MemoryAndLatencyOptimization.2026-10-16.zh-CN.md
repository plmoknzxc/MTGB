# 客户端与服务端内存、长局延迟优化

发布状态：本轮成果已随 [2026-10-16 合并更新](Release.2026-10-16.zh-CN.md) 构建，桌面客户端已覆盖，公网已部署 Linux14 并启用堆回收启动脚本。下文“未覆盖／未部署”保留其原测试批次时间点，具体发布及健康证据以新发布记录为准；原性能数字仍属于各自受测构建和场景。

本批承接 10 月 15 日诊断，10 月 16 日按用户要求恢复：核对暂停后的功能改动，完成两端优化及有界性能验证。公网服务器、桌面旧包的覆盖与发布另行记录，不以本机测试代替部署结果。

## 已确认的问题与改动

- 原录像记录器逐步保留双方视图的完整对象副本。相同冻结输入在 Unity 记录 1000 帧，原实现保留约 73.95 MiB，耗时约 1937 ms，超过 8 MiB 回归门槛。现在逐帧冻结、压缩写入临时文件，结束时流式生成兼容的 MTGBR1 录像；对局过程中不再保留完整时间轴对象图。省略录像中 null/零值字段，网络字段、隐私投影及录像原容量限制保持原合同。磁盘失败、容量限制均关闭记录，不得使正常对局中止。
- 服务端同步发送直接序列化当前席位视图；对外 `GetView` 仍返回独立副本。快照校验哈希改为流式 UTF-8/SHA256，保留原字段顺序、转义和旧服务器字段兼容性。
- 客户端创建的 Forge 主机也启用已有的按需卡库加载。原生准确牌号、卡组外生成牌查询与全卡名枚举分别核对，不将局部加载当作全卡库未缺失的证明。
- 卡组网格和拖动使用独立 256 像素缩略图；详情和战场维持大图。缩略图 GPU 缩放避免 CPU 双线性循环和读回；不支持相关复制能力的平台保留 CPU 回退。大图/缩略图的缓存预算分别为 128/96 MiB，淘汰无 UI 引用的旧图，保护包括缓存窗口在内的引用；全部被引用时预算为软门槛，不销毁仍被引用的图片。
- 每 0.5 秒的偏好控件发现仅绑定新控件；已有文本按自身偏好修订更新。战场每帧不再构造整体重绘字符串，也不再反复 JSON 序列化未变的玩家信息。昵称、席位、连接、组牌、准备状态、胜场、视图哈希和显式交互失效仍能触发更新。
- 新包无卡图的实际对局复现了另一条客户端慢路径：相同缺图在每次牌面刷新时遍历大量印刷版本和不存在的目录。增加有界的目录存在性/缺图查询复用，首次跳过不存在的目录，短期重复查询直接回退占位；大图发现新文件时同步释放缩略图的旧缺图结果。下载及导入/删除在通知 UI 前立即失效，手工复制文件最长约一秒后重新检查。已有卡图仍同步读取，不进入这个缺图等待窗口。初版文件通知及两级缓存交叉失效的失败均保留，最终不依赖平台文件通知实现。

暂停后的卡组曲线、数量显示、手牌扇形/横向浏览、昵称、通知和下拉框改动均保留。本批只修改它们实际共用的刷新检测边界，没有撤回其功能。最新四个 `BridgeCardNotices*.class` 与源运行包逐项比较；平台裁剪、Java 替换会重新计算包内 runtimeHash，不能要求它等于源运行包的总哈希。

### 最终发布包的固定条件长局

`linux-network/summary.json`、`resources.json`、`replay.json` 与原始日志/逐秒采样：Linux 本地文件系统，MemoryHigh=750 MiB、MemoryMax=900 MiB、MemorySwapMax=256 MiB、CPUQuota=125%、Java 最大堆 384 MiB；两客户端验证包的外部 CardImages 目录全程为空。

- 两真实客户端完成对局，服务器接受 **1161 次操作**，**1163 帧**录像可按收到的格式读取完整时间轴和预览，赢家席位 2、时长约 205.1 秒，文件约 1.80 MiB。1099 个由驱动跟踪的操作响应，双方前段 P95 约 **93.8/98.7 ms**、末段约 **273.4/275.1 ms**。后段开销仍随当前场面/快照增加，不解释为恒定延迟；此场景未复现反复等待数秒。
- 服务器进程组峰值 **750.4 MiB**，未触及 900 MiB 上限、无 OOM、无交换内存。触发软门槛 high **522 次**，全部运行累计 full memory stall 约 **12.5 ms**，所有采样 full avg10 为 0.00。不能写成“high 为零”；它与旧现场长期约 82–85% 的停顿不同。
- 由 Windows PSAPI 独立采样，两客户端工作集峰值约 **769.7/736.4 MiB**；暖机/末段中位数约 **738.8→744.0 MiB**、**695.7→718.4 MiB**。这是无卡图包的明确场景，不能与旧客户端在其他场景的 1.25 GB 直接计算降幅。Mono 自报 Process.WorkingSet64 为零，不使用那些值。
- 两客户端均正常退出，在线配置文件恢复，隔离的 Linux 单元正常停止。主编辑器返回 Main、停止运行、场景未修改，导入 worker 数恢复 8。公网服务仍为原 PID 371370，Native Java PID 402507，其他服务 PID 也未变化。

Windows 客户端：`Builds/ClientMemory1016/`；Linux 服务器：`Builds/LinuxServerMemory1016/`；可发布的服务器压缩包 `.tools/server-memory-1015/LinuxServerMemory1016.tar.gz`。客户端程序集 `6a8e099843b70274075960232042072aa0d2bbf9ba9bd9fae4b54d5b3fc7c764`；Linux 为 `77e2e3cb6342c08d786d1cdcff3f389ba0526dc199b5d5e2e2ef73b703265f6e`。上述长局固定在原运行包身份，后续全卡库优化仅追加原生覆盖类，程序集未重新构建；本节长局没有冒充新原生包的再次长局。当前包身份与新验证见下节。公网重启与桌面覆盖尚未执行，因此本记录不是线上已修复或 WAN 长局已验证的声明。

### 原生全卡库加载增量

用户追问显式全卡库枚举耗时后，继续分段计时并采样实际 `StaticData.ensureAllCardsLoaded`。定位到 `CardDb.loadCard` 为每张牌遍历全部系列，再逐系列查询印刷记录；34,457 个普通卡面名字的最终枚举本身仅约 20–25 ms。该入口由普通命名、随机生成/复制等原生流程调用，不只存在于压力测试。

`NativePatches.json` 追加两个有源文件哈希和唯一上下文守卫的补丁：`CardEdition.Collection` 共享一次构建的大小写不敏感牌名→系列索引，保留原系列遍历顺序，添加/追加自定义系列时失效；`CardDb` 合并原名、传入名和所有功能异名的候选系列，继续使用原 `addFromSetByAnyName`、印刷去重、卡面、异名和默认图版本选择。原有 45 个补丁保留；重编译后，原先已覆盖的 class 文件哈希均未改变，新增 15 个 CardDb/CardEdition 类文件。没有修改卡牌规则脚本、协议字段或 Unity UI。

## 客户端工作集继续优化（本轮）

用户追问 770/736 MiB 后，新增 `.tools/client-memory-1016/` 独立证据。先按当前 UI 源码重建基线；这次基线为 727.4/717.2 MiB，与历史 769.7/736.4 MiB 的程序集不同，不将两者直接相减作为本轮降幅。

- 入站视图由逐令牌读取同时计算发送方哈希，移除整棵 JObject、中间 JSON 和 UTF-8 数组；保留未知字段参与校验、原字段顺序、旧版本缺省字段、席位/对局/序号守卫与解析后篡改检测。压缩信封直接读取 MemoryStream 的有效区间，继续使用原容量与严格 UTF-8 检查。实际源码链接的 .NET 9 夹具，21,462 字节输入每次解析和校验分配约 673,335→134,091 字节，降低约 80%；此数字不是 Unity 进程 RAM。Unity 45 项边界检查通过，含旧服务器两席位真实起手、七张私有手牌及错误席位/对局/过期视图拒绝。发送端规范 JSON 兼容性已验证，不对重复属性的非规范输入承诺旧 JObject 折叠行为。
- 客户端预生成卡库改为顺序 FileStream，复用字符串读取缓冲，不再先读取完整约 23 MB 文件或逐字符串生成临时 byte[]；服务器的按需解码支路保留。97,784 条印刷的全部字段/牌面/规则文字/背景文字与原 JSON+flavor 比对一致；缺文件、截断、版本/哈希不匹配和取消边界通过。
- 开发构建的真实堆快照沿静态字段、GCHandle 与值类型/数组引用核对，找到 97,784 张常驻卡牌和 97,080 条搜索记录。搜索数据按首次发现归属约 42.4 MiB；该归属不是支配树 retained size。约 23 MiB 是重复牌名、稀有度、系列名、画师和版式字符串，改为一次读取内按 Ordinal 共享。全部搜索记录逐字段一致，36,692 个不同标签共享引用；临时共享索引在读取后释放，不建立全局永久字符串池。原始对齐扫描包含死对象头，不能据此声称图片缓存闭包泄漏。
- 图片缓存预算检查的捕获闭包移至确需淘汰时调用的函数。预算内连续 100,000 次检查实际托管分配为 0。大图/缩略图预算、正在显示及隐藏窗口图片保护、同步加载路径维持原行为。

## 保留的失败与验证限制

1. 第一版长局夹具错误使用单条 500 张，违反每条 250 张的入口限制；改为两个准确牌号各 250 张。失败保留。
2. 原长局记录达到 256 MiB 明文上限后，`InvalidDataException` 未被 IOException 捕获，导致对局中断；已显式隔离容量失败并缩减录像字段，当前真实 1000 次操作通过。旧失败保留。
3. CPU 缩略图冷载入约 15.7 ms，曾慢于原大图；该路径在当前 GPU 平台已替换，回退平台性能未作同等承诺。
4. 编辑态运行图片验证触发 Unity 的 Destroy 编辑态限制；该尝试不作为有效图片性能证据。清理测试瞬态对象后在 Play Mode 重跑，控制台零错误。
5. 旧环境下 384 MiB Java 堆的显式全卡名枚举超过 60 秒；768 MiB 上限下约 44.5 秒。后续增量已修正反复遍历系列的热点，并在 384 MiB 下通过，见上节；旧超时与耗时原样保留，44.5 秒与本次受控测试并非同环境，不能直接计算提速倍数。线上堆或服务限制未调整。
6. 图索引存在文件元数据变化标记，相关结论使用当前准确源码回读补证。分类清单只刷新，2582 个未登记/318 个需重测不是本批规则效果数量；历史机制身份和暂停中的全机制目标未改变。
7. 首次 Linux 构建的 C# 编译器报告 Out of memory。诊断时本机仅约 182 MiB 可用物理内存，长时间运行的主编辑器提交约 28 GiB、两个资源导入子进程各约 4.7/5.1 GiB。临时将 Unity 导入 worker 从 8 减为 1，释放资源后重试；不把构建进程的资源不足记成游戏运行测试失败，也不改变游戏或线上服务预算。长局驱动同时补弃牌选择的已选/禁用与确认候选处理，避免把驱动无法推进误报为游戏长局阻塞。
