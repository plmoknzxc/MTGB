# MTGB 联机开发待办

## 目标

联机采用独立权威服务器模型：客户端只提交操作意图，服务器持有完整规则状态、验证 `GameAction`、推进规则并发送每个玩家允许看到的结果。

本文只记录尚未完成或尚未经过真实联调的内容。现有协议与启动方式见 [OnlineMultiplayer.zh-CN.md](OnlineMultiplayer.zh-CN.md)。

## 当前基础

目前已有：

- Unity Netcode for GameObjects 与 Unity Transport 接入。
- 独立服务器和客户端启动代码。
- 两个玩家席位、显示名和重连令牌。
- 牌组提交、复制数量检查、准备和权威随机种子开局。
- 客户端只提交 `GameAction`，服务器独立验证后按玩家发送脱敏视图；客户端不再预测隐藏状态。
- 动作序列、状态序列、玩家视图哈希和脱敏快照重同步。
- 断线席位保留、重新连接、认输和对局结束消息。
- 主界面的联机大厅入口及玩家 1/2 本地视角映射。
- v7 内容清单握手、消息防护、房间注册表、多对局会话和项目级验证。
- 服务器每局随机决定先手，双方按先手顺序完成伦敦调度，客户端显示先后手并只接收自己可见的调度选择。
- BO1/BO3 系列比分、局间换备、60 张主牌/15 张备牌合法性、系列结束与重新准备。
- 联机入口拆分为连接/建房页与房间准备页；连接后可更换已保存牌组，不再和连接设置挤在同一页。

P0 与 P1 的代码和自动验证已经完成；正式发布、长期压力测试、账号匹配和运维仍属于 P2。

## P0：完成可测试的双人对局闭环

### 已完成：1–5

- 已通过 Multiplayer Play Mode 提供一个服务器加两个客户端的本机联调环境。
- 两个客户端分别保存玩家名、牌组、端点和重连令牌；联机日志包含对局 ID、席位、动作序号和状态哈希。
- 已接入 `Idle`、`Submitting`、`Resyncing`、`Disconnected` 交互状态、请求 ID、规则输入锁、十秒超时、拒绝恢复和权威重同步。
- 所有 `GameActionType` 使用统一协议通道；项目验证覆盖协议往返、双客户端确定性镜像和权威回放恢复，规则层验证覆盖选择、施放、战斗与复杂卡牌特性。
- 客户端掉线后在 30 秒宽限期内自动重连；重新认证后重载对局并保持输入锁，权威回放哈希确认后才恢复操作。
- 服务端在宽限期内保留席位、牌组和重连令牌；超时后由仍在线的对手获胜，双方均不在线时终止对局，并拒绝错误或过期令牌。
- 自动回归覆盖重复/乱序请求、伪造席位、过期状态序列、输入超时、重连窗口、故意哈希偏差和权威回放恢复，并已接入项目级验证。

### 1. 双客户端联调环境（已完成）

- 提供无需正式发布的本机联调方式，可同时运行一个服务器和两个客户端。
- 支持为两个客户端设置独立的玩家名、牌组和重连令牌存储。
- 增加开发日志中的对局 ID、席位、动作序号和状态哈希。
- 联机功能稳定之前不执行正式独立服务器构建。

验收：两个客户端可连接同一服务器、提交不同牌组、准备并进入同一场对局。

### 2. 异步动作确认与输入锁（已完成）

客户端当前调用规则接口后，需要等待服务器接受动作才能获得真实状态。需要统一处理这段等待期：

- 增加 `Idle`、`Submitting`、`Resyncing`、`Disconnected` 等客户端交互状态。
- `Submitting` 时禁止再次提交规则动作，但允许设置、全控开关等纯本地操作。
- 选择目标、确认施放、支付费用、声明攻击和阻挡必须在服务器确认后刷新下一步 UI。
- 动作被拒绝时恢复原交互状态，并显示服务器返回的具体原因。
- 为网络请求增加超时，不能永久停留在“等待服务器”。

验收：快速连点、拖动多张牌或连续点击阶段按钮不会产生重复动作，也不会让 UI 与服务器状态分离。

### 3. 完整规则流程联调（已完成自动验证基础）

依次验证以下动作在两端结果一致：

- 起手、调度、抓牌、主阶段和阶段推进。
- 地牌、产费、撤回未使用法术力。
- 施放咒语、选择或重选目标、取消、确认、堆叠与优先权。
- 搜索牌库、弃牌、多选、数字选择和伤害分配。
- 生物攻击、阻挡、多个阻挡者、战斗伤害和状态动作。
- 双面牌、历险、房间、传纪等 `CardFeatureRuntime` 路径。
- 认输、正常胜负、平局及对局结束后退出。

验收：自动验证已确保每个已接受动作后两端动作序号与权威状态哈希一致，并验证权威回放恢复。本机三实例已验证独立服务器、两个隔离客户端进入同一 matchId、加载同一战斗场景并完成初始权威哈希同步；每次规则/UI 扩展后仍应重复人工交互冒烟。

### 4. 断线重连闭环（已完成）

- 战斗场景中显示断线与重连状态。
- 重新连接后恢复席位、当前回合、步骤、优先权、堆叠和正在进行的选择。
- 重放期间锁定规则输入，完成哈希确认后再解锁。
- 服务端设置重连宽限时间；超时后按规则判负或终止对局。
- 处理双方同时断线、服务器主动断开和错误重连令牌。

验收：在施放确认、目标选择、牌库搜索和战斗中分别断线，重连后都能继续对局。

### 5. 自动化网络回归（已完成）

- 增加协议往返、重复包、过期动作序列和非法席位测试。
- 增加相同种子、相同牌组、相同动作流得到相同哈希的测试。
- 增加故意制造哈希差异后由权威回放恢复的测试。
- 增加断线、重连和重连超时测试。
- 将网络验证接入 `MTGB/Validate Project`。

验收：核心网络测试可在无人工点击的情况下重复运行并稳定通过。

## P1：达到公网可用的安全边界（已完成）

### 已完成：6–9

- 服务端为两个席位分别投影玩家视图；隐藏手牌和牌库只包含数量对应的临时负 ID，不含卡牌身份，重新进入隐藏区后旧 ID 失效；面朝下公开对象只暴露公开特征，不向非控制者暴露印刷身份。
- 开局、动作确认和重同步只发送对应席位的脱敏视图，不再向客户端发送双方牌组或完整权威回放。
- v7 握手校验游戏版本、协议版本、数据库模式版本和卡牌数据库/Lua 的 SHA-256 内容哈希。
- 服务端校验已安装卡牌、房间允许系列和自定义内容开关；非核心数据库内容默认视为自定义内容。
- 已加入消息读取上限、字符串/牌组/操作字段上限、滑动窗口限流、心跳、空闲断开、请求超时和单调请求 ID。
- 房间号可创建、加入或退出独立房间；大厅可配置并显示生命值、每局随机先手、系列规则、自定义内容规则和准备状态。
- 每个房间持有独立 `OnlineMatchSession`，动作仅在所属房间重建并推进权威规则状态；结束后释放规则对象、运行时卡牌、Lua 监听、回放和断线席位。
- `mtgb_validate_p1` 自动覆盖视图脱敏、篡改检测、内容不一致、恶意字段、限流、房间配置和双房间状态隔离，并已纳入项目验证。

### 6. 隐藏信息隔离（已完成）

当前客户端为了运行完整确定性镜像，会获得双方牌组数据。UI 虽然隐藏对手手牌，但仍可从进程内存读取，因此不能作为正式公网版本。

需要新增服务端到玩家视角的投影层：

- 服务端保留完整 `GameRules`，客户端不再持有对手完整牌组和隐藏卡牌定义。
- 对手牌库和手牌只发送数量、公开属性及不可推断身份的临时对象 ID。
- 卡牌被展示、施放或进入公开区域时，服务器发送揭示信息。
- 卡牌重新进入隐藏区域时，根据 CR 需要使旧对象身份失效。
- 分别生成玩家 1、玩家 2，以及未来观战者的快照。
- 重同步发送对应玩家的脱敏快照，不能发送完整服务端回放。

验收：检查客户端内存和网络包，无法获得尚未公开的对手手牌或牌库顺序。

### 7. 内容与协议版本握手（已完成）

- 握手时校验游戏版本、联机协议版本和数据库模式版本。
- 对参与对局的数据库、Lua 脚本及必要规则资源计算内容清单或哈希。
- 内容不一致时拒绝准备，并明确指出不一致项目。
- 服务器只允许牌组引用已安装且允许使用的系列与卡牌。
- DIY 内容需要房间规则明确允许，并且双方与服务器内容一致。

验收：修改任意一张参战卡的数据库记录或 Lua 脚本后，旧客户端不能进入该场对局。

### 8. 网络健壮性与恶意输入防护（已完成）

- 心跳、连接超时、请求超时和空闲超时。
- 限制消息大小、发送频率、牌组大小和字符串长度。
- 拒绝伪造玩家 ID、对象 ID、选择请求 ID和未来或过期动作序号。
- 所有非法动作只返回错误，不能使服务器抛出异常或改变状态。
- 为重复消息提供幂等处理，避免网络重试造成重复结算。
- 日志不能记录重连令牌、完整隐藏牌组或其他敏感数据。

验收：模糊输入、恶意大包和高频请求不会导致服务器崩溃、内存持续增长或状态被修改。

### 9. 房间与多场对局（已完成）

服务端已拆分为服务进程、房间和对局实例：

- 创建、加入、退出房间和房间号。
- 房间配置、每局随机先手、牌组规则及准备状态。
- 一个服务进程并行管理多个互不影响的 `MatchSession`。
- 对局结束后释放 `GameRules`、Lua 环境、回放和连接状态。
- 玩家不能跨房间引用对象或提交动作。

验收：同一服务端同时运行多场对局时，动作、日志和状态完全隔离。

## P2：部署、运维与扩展

### 10. 对局记录和可观测性

- 生成唯一对局 ID，并记录双方账号或临时身份、版本和结束原因。
- 结构化记录动作序列、拒绝原因、重同步次数和网络延迟。
- 保存可重放的权威对局记录，但对普通玩家导出时处理隐藏信息。
- 增加服务器健康检查、在线人数、房间数、对局数和错误统计。

### 11. 账号、匹配与持久化

- 账号认证和短期会话令牌。
- 牌组上传与服务器侧保存。
- 好友房间、匹配队列、取消匹配和匹配超时。
- 对局结果持久化及重复提交保护。

这部分应独立于规则服务；不要把账号数据库逻辑写入 `GameRules`。

### 12. 观战和其他扩展

- 观战者只接收允许公开的信息，并支持延迟观战。
- 聊天、表情和举报系统使用独立消息通道。
- 后续再考虑比赛房间、裁判视图和断点恢复。

### 13. 独立服务器构建与部署

在 P0、P1 稳定后再执行：

- 清理并固定 Dedicated Server Build Profile。
- 构建 Windows 或 Linux 无头服务器。
- 配置公网 UDP 端口、防火墙和云安全组。
- 完成服务器启动参数、配置文件、日志目录和优雅停机。
- 进行长时间运行、并发对局和内存压力测试。
- 建立可重复的自动构建与发布流程。

## 推荐执行顺序

1. 双客户端联调环境。
2. 异步动作确认与输入锁。
3. 完整规则流程联调。
4. 断线重连闭环。
5. 自动化网络回归。
6. 隐藏信息隔离。
7. 版本与内容握手。
8. 网络防护。
9. 房间和多场对局。
10. 最后构建并部署独立服务器。

完成第 1 至第 5 项后，联机可供开发阶段稳定测试；完成第 6 至第 9 项后，才适合进入公网测试。
