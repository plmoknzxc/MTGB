# Forge 底层迁移计划

更新日期：2026-09-30。当前引擎已升级为 Forge 2.0.15，提交 `4ec5f1a2c32fa90ecb983a72b9eb47aa5c5d7676`；见 [同步记录](ForgeUpdate-2.0.15.zh-CN.md)。下文最小验证保留迁移时的历史版本。

状态：阶段 A–D 的实现、旧核心清理及最终 Windows 构建回归已完成；详细结果见验证记录。Forge 是唯一规则底层。后续追加的 MTGAPrototype 战场接入见 [战场说明](ForgeBattlefield.zh-CN.md)；下方 A–D 保留最初迁移范围，DIY 仍为后续范围。

实现、构建和验收入口见 [ForgeBridge 说明](../Tools/ForgeBridge/README.zh-CN.md)。最新检查点见 [迁移验证记录](../Tools/ForgeBridge/Reports/验证记录.zh-CN.md)。

## 1. 已确认的方向

- Forge 作为唯一规则执行底层；官方卡及未来 DIY 都使用 Forge 卡牌脚本。
- 彻底退出 Lua，不维护两套规则系统，不建设长期 Lua 兼容层。
- 保留 Unity 客户端、现有组卡、大厅和联机体验。
- 本轮支持 Windows 局域网建主和独立服务器。
- 本轮不包含正式战场 UI 交互、选择面板、费用面板和动画适配。用独立调试入口验收客户端操作。
- 后续正式战场适配沿用 `MTGAPrototype`，不在本轮切换 `IntegratedBattlefield`。
- DIY 编辑器、旧 DIY 内容迁移后续处理；本轮不增加离线 AI 或多人 Commander。

## 2. 已完成的最小验证

固定 Forge 提交：`746455d75515daabec62971e0544cf19c66356b3`。后续接入先沿用该版本；权威端升级时重新验证。联机客户端只需兼容通信协议，规则以实际运行 Forge 的房主或独立服务器为准。

真实规则链：下地 → 产费 → 施放官方闪电击 → Forge 请求目标 → Unity 提交玩家选择 → 支付费用 → 双方让过优先权 → Forge 结算生命 20 → 17。

- Unity Play Mode、Windows 隐藏窗口和可见窗口，各三轮通过。
- 本测试的非法目标、重复响应、席位手牌投影和进程退出检查通过。
- 启动至首个请求约 5～7 秒，实际 JVM 驻留内存约 565～624 MiB。
- 原型只覆盖这条交互链；没有完成现有牌组映射、房间接入、通用目标候选、完整隐藏信息及全卡交互适配。

## 3. 架构与接口方向

运行结构：Unity 客户端 → 现有联机服务器 → Forge Java 适配进程。局域网主机承担服务器角色，独立服务器使用同一会话实现。

- 当前每个活动对局独立进程，已验证两房间同时运行及单进程故障隔离；尚未进行生产容量压测。
- Forge 持续持有对局状态，替换旧会话每次恢复回放并创建 `GameRules` 的执行方式。
- 客户端只提交输入并显示权威状态；Java 侧的规则线程、输入接收和 Unity 主线程分开调度。
- 会话接口覆盖创建、提交输入、读取席位状态、认输、结束与资源释放。
- 选择请求携带会话、席位、请求标识、候选和约束；目标、费用、排序等按实际机制逐步适配。
- 入房校验客户端通信协议；权威端开局检查本地引擎与桥接配置。双方资源哈希不作为连接条件，完整资源检查只在显式验证或重载时执行。
- 原型的一条消息含两份席位视图，仅用于本机模拟两人。正式联机必须按认证连接分别发送允许看到的状态，不能原样转发原型消息。
- Windows 客户端和原生独立服务器包均携带匹配的 JRE、官方资源及对应源码，使用相对路径和文件哈希清单。

## 4. 实施顺序与完成标准

### 阶段 A：官方卡池与组卡

- [x] 加载固定 Forge 版本的完整官方目录与原有脚本，不逐张重写效果。
- [x] 接入现有搜索、筛选、展示、组卡保存和加载；解除这些路径对 Lua 校验和旧规则执行对象的依赖。
- [x] 保留 `.mdk` 主牌、备牌及印刷身份，建立 `SET/COLLECTOR` 与 Forge 印刷条目的映射。
- [x] 缺失或无法唯一映射的条目明确报错，不静默替换卡牌，不自动删卡或改写旧牌组。
- [x] 实际保存的官方 `.mdk` 牌组能够交给 Forge 创建对局。

### 阶段 B：现有联机接入

- [x] 替换 `OnlineMatchSession` 的旧核心执行链，保留现有网络传输、房间、席位、准备和房主开局流程。
- [x] 两个真实客户端通过现有大厅提交牌组并开局，由调试入口响应 Forge 请求、推进对局。
- [x] 接通 BO1/BO3、系列比分和局间换备，保留注册卡池约束与房间内容限制。
- [x] 局域网建主和独立服务器两种入口均跑通。

阶段检查点：先验证“现有牌组 + 现有房间 + 两个客户端”能完成一局，再据实际剩余问题更新排期。

### 阶段 C：协议与可靠性

- [x] 校验认证席位、请求序号、候选范围及当前选择状态；拒绝重复、过期和越权操作。
- [x] 逐连接生成脱敏状态，验证手牌、牌库和已接入机制涉及的隐藏信息；复杂隐藏机制未通过前明确限制使用。
- [x] 保留断线宽限与房主退出行为；重连恢复当前快照和未完成选择，避免重复支付或重复结算。
- [x] 验证通信协议不兼容时拒绝连接，以及多房间状态和故障隔离。2026-09-24 起允许双方本地内容不同，卡组由权威端检查。
- [x] Forge 进程故障时明确异常终止受影响对局，不判玩家失败。首版不实现服务器崩溃后的对局恢复。
- [x] 验证启动、正常退出、取消和异常退出的进程清理；完成 Windows 打包检查。

### 阶段 D：切换与清理

- [x] 新链路验收前保留旧核心作为参考；验收后移除旧规则及 Lua 运行时、绑定接口、专属加载和握手依赖。
- [x] 停止扩展 Lua SDK、Lua 模板和卡文转 Lua 功能；后续 Data Editor 统一转向 Forge。
- [x] 检查保留界面对旧核心的编译依赖，拆出仍需使用的展示和资源类型；正式战场尚未适配的操作明确标示，不保留隐式旧引擎执行路径。
- [x] 移除 Lua DLL 和资源后，正式客户端与服务器仍可编译、启动、组卡并通过调试入口完成对局。
- [x] 更新验证入口、构建与文档。旧代码以 Git 历史保留，不维护旧版运行入口。

本轮最终验收：两种联机方式均通过双客户端 BO3、换备、选择中重连、重复请求、脱敏和进程清理检查；正式战场 UI 可玩性不属于本轮验收。

## 5. 全卡接入的边界

- 完整目录可浏览、组卡，固定版本中的官方效果脚本直接复用。
- “目录和脚本已加载”“交互已适配”“行为已验证”是三个独立状态；不把目录数量当作完整可玩性证明。
- 本阶段调试接入不以逐卡验证清单阻止提交，但必须显示未适配、未验证范围；不支持的交互明确失败，不自动替玩家选择。
- 面向正常玩家开放联机卡池时，按通过验证的范围分批开放；不承诺一次验证所有官方卡及组合。
- 中文资料缺失时可显示英文，卡图缺失时显示文字卡面；补齐全部中文和卡图不在本轮范围。

## 6. 后续 DIY 与兼容处理

- Data Editor 保留基本信息、中文编辑和卡图功能，效果编辑及模板生成目标改为 Forge 脚本。
- 常规效果由脚本表达；已有脚本能力无法表达的新机制扩展 Forge Java，必要时增加 Unity 交互与联机字段。
- 内容包包含 Forge 脚本、系列信息和卡图，具体格式在 DIY 阶段确定；权威端检查所需卡牌和房间许可，客户端本地内容不决定规则结算。
- 旧 DIY 文件保留为迁移素材，Lua 不在新底层执行。模板效果可评估批量转换，手写效果逐张迁移和验证。
- 旧回放不要求在 Forge 播放；首版保留对局历史与诊断记录，新完整回放播放器后续规划。
- 执行卡牌内容或编辑器迁移前，完整阅读并同步更新 [制卡契约](CardDataAuthoring.zh-CN.md)，落实保存、重载、结构和实际对局验证。
- 固定并记录 Forge 来源、修改和许可证，正式分发落实适用的许可证及对应源码交付要求。
