# 对局开局加载优化（2026-10-26）

本批针对用户反馈“进入对战后等很久才出现起手”，不恢复其他机制盘点任务，不修改卡牌脚本、洗牌、调度规则或网络协议。当前实现已写入源码和项目 `ForgeRuntime`；桌面安装版和生产服务器尚未覆盖。

## 原因与修正

实际桌面安装包的 Java 引擎单独启动即可复现等待，因此先处理引擎端热点。隔离计时中，约 6.4 秒的一次开局有约 4.4 秒处于 `FModel.initialize`。进一步探针发现 `CardStorageReader` 读取预生成的 35,240 名称索引时，仍重新遍历全脚本目录计数，并对每条索引调用 `File.isFile`；这是每局重新启动的权威 Forge 进程重复执行的磁盘工作。

`NativePatches.json` 的 `server-prepared-card-name-index` 修正为只解码和检查预生成索引。保留魔数、版本、数量上限、重复名字、路径边界、扩展名、截断和尾随数据检查。脚本文件存在性／可读性延后至真正加载对应卡牌时，继续通过原 `Files.newInputStream` 明确报错，不用空牌或占位效果替代。

这有一项检查时机变化：安装中**与当前对局无关**的脚本缺失，不再仅凭文件计数在每局开场被发现；索引生成和显式运行清单完整性检查仍检查完整安装内容。运行清单不是自动每局执行一次的全盘校验。普通 Forge 未设置预生成索引属性时的读取／构建索引路径保持原样。

## 证据与范围

证据集中在 `.tools/opening-latency-1026/`，最终逐轮交替 A/B 结果见 `alternating/result.json`。该测试使用同一桌面运行包、自带 JRE、同一台机器和保存的 4C／红白 token 牌组，候选只在 classpath 前置本批 `CardStorageReader` 类。计时起点为启动进程，终点为收到双方七张起手的第一个调度请求；不含从大厅点击、联网传输和 Unity 画面资源全部完成的时间。两版本交替运行，避免把初次文件缓存差异当作提速。

- 初次未受控冷启动观察为 27.24 秒；随后一局约 6.26 秒。没有清理系统缓存或重启机器作严格冷启动对照，不能据此承诺冷启动降幅。
- 第一组各三次比较的中位数为 7.79 → 3.98 秒；其中基线首轮与编译有部分重叠，仅作初步观察。正式性能结论使用后续顺序交替比较，不混入编译、全目录哈希和全卡库枚举。
- 正式三轮交替的旧版为 11.95／11.95／10.83 秒，候选为 5.73／5.64／5.82 秒，中位数 **11.95 → 5.73 秒，减少 52.05%**。各批次仍受机器后台负载和文件缓存影响，绝对秒数不能当作所有设备或线上延迟承诺；只比较同一批次的前后结果。
- 各次双方初始牌名／顺序一致，双方真实调度一次、伦敦放底、进入优先权、认输结束均通过；这只验证这些开局流程，不是整张卡牌或完整对局效果通过。
- 本地 AI 实际开局、玩家调度／放底及正常结束通过。法禁实际六张保留、100 张争锋第一次免费调度／七张保留和正常结束分别通过，证据为相应独立运行的原始请求。
- `PreparedCardNameIndexFixture` 的 15 项 API 检查通过。修改前在“未使用的缺失脚本不阻塞索引读取”处失败；修改后缺失脚本仍在实际读取时抛错，损坏／越界索引仍被拒绝。原失败日志保留。
- Unity 中通过实际 `OnlineMatchSession` 使用项目原生运行包，收到双方七张起手并认输、结束、释放会话；主场景未运行或改动。首次与其他验证重叠的 9.82 秒保留；空闲后重复为 6.30 秒。此处是 Editor 会话接收证据，不是 Player 画面端到端性能对照。
- 原生补丁上下文组合及 JDK 17 编译通过；补丁源守卫 4 项和 C# 文本编码守卫通过。机制覆盖只刷新分类，原 2,582 个未登记／318 个需重测状态保留，不新增全卡池 PASS。

全卡库显式枚举的补充探针在**原桌面运行包**上超过 80 秒，已终止；本批不声明全卡库枚举通过或提速，也不将其冒充起手失败。测试驱动首次误将 MDK 当 JSON、未识别 `!side`、误猜伦敦 Auto 的 ID，以及 PowerShell 未引用 `-D` 参数的失败均保留；最终工具读取实际 MDK、使用原 `cancel` Auto 选项及生产 `respond` 消息。

## 复测

```powershell
python -X utf8 Tools/ForgeBridge/Test-OpeningLatency.py --runs 3 --check-index
```

可用 `--deck`／`--opponent` 指定保存的 MDK，`--runtime` 指定实际运行包，`--override` 前置隔离候选类；`--format brawl` 或 `--format duelcommander` 复核两类主将开局，`--ai-seat 2` 走真实 Forge AI。`--max-opening-seconds` 是测试阈值，`--baseline` 对相同牌组／起手断言中位数至少改善 25%；均不改变产品开局。

项目运行包只替换 `CardStorageReader` 三个 class，并同步对应完整源码／来源和运行清单，最终身份见 `workspace-runtime.json`。已安装客户端、旧发布包和服务器保持原身份；后续发布须携带该原生补丁并验证实际权威端，不能只更新 Unity 程序集。

## 追加：Java 编译线程（用户要求继续提速）

第二批证据在 `second-pass/`，与上述第一批分别保留，不把跨时段绝对秒数直接拼接。修正后的同一原生包仍有 JVM 启动／动态编译开销；探针中 `-Xms32m` 并未提速，而减少并发编译线程有明显收益。未设置 `TieredStopAtLevel=1`、未关闭 C2／分层编译，也没有限制游戏和 AI 的工作线程。

`OnlineMatchSession` 给普通对战设置 `-XX:CICompilerCount=2`；本地 AI 设置为 3，保留第二个 C2 编译线程。实际启动参数仍包含原有 UTF-8、独立 HOME、私有标准流、按需卡库等配置。无新协议字段或卡牌规则改动，项目原生运行包保持本批第一部分的身份。

| 同时段交替对照 | 原生包已含第一批优化，默认 JVM | 本次参数 | 中位数减少 |
| --- | --- | --- | --- |
| 4C／红白普通开局，三轮 | 5.69 秒 | 2.36 秒（2 编译线程） | 58.48% |
| 4C／红白 AI 开局，三轮 | 5.86 秒 | 2.98 秒（3 编译线程） | 49.14% |

所有上述流程均保持相同起手、玩家调度／放底、进入优先权及结束。`second-pass/alternating/result.json` 和 `second-pass/ai-opening/result.json` 保存原始逐轮数据；这是本机 Java 进程到起手请求，不是大厅到 Player 完成绘制或公网总耗时。

后续响应复核使用相同旧 AI 驱动的隔离副本和真实引擎。普通双方 800 次请求完成，默认／2 线程总耗时 39.46／34.62 秒；末 100 条响应中位数 44.77／51.57 ms、P95 58.79／63.53 ms，不能宣称每个响应百分位都改善。首次把 AI 也限制为 2 线程时，虽开局快，但短局的响应中位数 40.70→91.69 ms，候选被撤下，原证据保留在 `follow-on-result.json`。

改为 AI 3 线程后，两轮默认／候选自然对局总耗时分别 14.30／7.72、16.51／7.15 秒，均实际施放 Goblin Guide、造成战斗伤害并自然结束，均 75 次人类请求。响应中位数分别 98.04／62.65、105.23／59.05 ms，P95 分别 254.10／119.65、275.93／113.02 ms。限于这些有界 AI 场景；不是所有牌组的 AI 性能承诺。见 `ai-balanced/result.json`。

单独调试用的 FModel／启动探针曾出现约 43.6 秒的异常慢采样，该探针包含临时重新编译的模型类，未拿它当正式对照或产品故障结论。正式比较仅使用相同桌面原生包、第一批读取器覆盖层以及不同 JVM 参数。可用 `--java-option=-XX:CICompilerCount=2` 或 `=3` 重现参数实验；该选项只改变测试子进程，不会改写产品设置。

Unity 编译完成且控制台无错误。实际 C# 会话的普通／AI 子进程由 `jcmd VM.flags -all` 核实为 2／3 个编译线程，`TieredCompilation=true`、`TieredStopAtLevel=4` 均保持默认；双方七张起手、认输、结束及释放均通过。Editor 收到起手分别 4.42／2.95 秒，仅作该次消费者接收记录；验证钩子恢复为空，Main 场景未运行／未修改。另以 384 MiB 堆和两个处理器运行争锋开局、免费调度／保留及结束通过，不能据此声明已实测生产 Linux 延迟。
